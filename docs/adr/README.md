# 架构决策记录（ADR）

> **记「当初为什么这么定」。** 一次性的审查报告会被时间淘汰，但"为什么选这条路"在几年后仍然有用。
>
> 与 [技术债台账](../tech-debt.md) 的分工：台账记「已知的坏」，ADR 记「已定的好」。
> 一件事可能两边都出现——ADR 说决定，台账说这个决定的代价。

## 什么时候该写一份 ADR

满足**任一条**就写：

- 决策会**限制未来的选择**（例：多入口切法一旦定型，改域划分成本很高）
- 决策有**明确的代价**，且这个代价需要被记住（例：容器查询的兼容下限）
- 后来者**大概率会问"为什么不用另一种做法"**（例：为什么不发单入口靠 tree-shaking）
- 决策**改过一次**（那更该记，否则会有人再改回去）

不必写：日常实现选择、能靠代码自解释的东西、纯风格偏好。

## 格式

```markdown
# ADR-NNN：一句话标题

- 状态：提议 / 已接受 / 已废弃 / 被 ADR-XXX 取代
- 决策人：谁
- 关联：相关文件、闸口、债务编号

## 背景      为什么需要做这个决定（当时的约束是什么）
## 决策      决定了什么（要具体到可执行）
## 后果      正 / 负，都要写
## 复核触发条件   什么情况下应该重新审视这个决定
```

**「后果」里的"负"必须写。** 只写优点的 ADR 等于宣传材料，起不到决策记录的作用。
