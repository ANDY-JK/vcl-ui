# ADR-006：低代码部署形态——库只出「契约 + 参考实现」，不随包附 BFF

- 状态：**已接受**（#471 成文；实现早于此）
- 决策人：项目主 + AI 审查
- 关联：ADR-005 的 D2、TD-24、`src/components/form-builder/designer/rest-form-store.ts`、`examples/lowcode-backend/`、`docs-site/guide/lowcode.md` §3

---

## 背景：台账与 ADR 互相打架

`docs/tech-debt.md` 的 **TD-24** 长期写着「部署形态未定：A 用户自有后端调 API / B 随库附 BFF / C 未定」，
目标栏是「需求方答复后」，理由是「需求方多次追问未答复」。

但 **ADR-005 的 D2 已经把这件事定了**：

> 「库内打包一个 BFF ❌ 那是另一个项目（服务端 + 部署 + 运维），不是组件库能力」

也就是说：**库的产品定位本身就是 A**（前端组件库 → 宿主自己的后端），
不是「等需求方在 A/B 之间选」。把「库要不要附 BFF」当成一个悬而未决的外部问题，
等于让一个**已经由库作者作出的定位决策**伪装成外部依赖 —— 台账会永远停在 `open`，
后来者也会以为还有一轮没做的选型。

## 决策

**默认形态 = A，且这是库的能力边界，不是待选项。**

| 形态 | 结论 | 理由 |
| --- | --- | --- |
| A 宿主自有后端 + 库出 REST 契约与参考实现 | ✅ **已交付** | `createRestFormStore`（9 方法）、`examples/lowcode-backend/`（内存 / SQLite 两套存储）、`docs-site/guide/lowcode.md` §3 契约 |
| B 随库附 BFF | ❌ **明确不做** | ADR-005 D2：服务端 + 部署 + 运维是另一个项目；打包进组件库会把 Node 运行时、数据库驱动、鉴权运维一起变成库的依赖 |
| C 未定 | ❌ 已消解 | A 是默认，B 是「若某个宿主自行要做」的增量，不构成库的待决项 |

**B 若要发生，它是宿主侧的净新增，不是库的缺件**。清单（供真要选 B 时估工，
而不是留给后来者"好像还欠一层"）：

1. 一个服务端进程（路由转发 `/forms` `/records`，令牌校验 / 刷新 / 轮换）；
2. CORS、限流、审计日志、部署与监控（库不管运维）；
3. 与宿主现有账号体系对接（库只收 `baseUrl` + 令牌，不认身份源）；
4. 并发写协调与连接池（参考后端刻意没做，README「上线前要补的」已列）；
5. 版本化契约与灰度（库的 `RestStoreConflictError` 只负责把 409 如实抛给宿主）。

## 后果

- **库侧可机械验证**：`src/` 不得引入任何服务端运行时（`node:http` / `node:sqlite` / `express` / `fastify` …）；
  `createRestFormStore` 必须继续从公共面导出；参考后端的路由表必须覆盖客户端实际发出的路径。
  这三条由 `tests/unit/lowcode-deployment-adr.spec.ts` 钉住（#471）。
- **TD-24 重新定性**：不再是「等答复」，改为 `accepted` + 触发条件「某个宿主明确要求随库附 BFF」
  —— 那时按上面 5 条估工并新开 ADR，而不是把库改成服务端项目。
- **文档口径**：`docs-site/guide/lowcode.md` §3 继续以 A 为唯一写法；不写「B 待定」。

## 反例（不作为决策依据）

- 「需求方没回，所以先两种都留着」—— 留着的是**未决状态**，不是能力；它让闸口、文档、台账各说各话。
- 「加个可选 BFF 包，反正没人用」—— 可选依赖一旦进 `src/`，`check:deps` / 多入口构建 / SSR 全部要跟着兜。
