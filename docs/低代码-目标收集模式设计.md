# 低代码「目标收集」模式设计（2026-08-31）

> 状态：**已实现（2026-08-31）**，返利函/陈列/合同三个目标收集实例全部验证通过
> 背景：返利函/陈列/合同三个业务本质同类（门店资料 + N 个照片位），但现有低代码只有「单页模式」（一张表单提交一条记录）；门店清单形态（ContractCollectionDemo：目标表格 + 每行上传位 + 状态/搜索/导出）实际业务最常用，需进低代码体系。

## 一、问题

1. 三个业务模板（rebate/shelf/contract）是「单门店表单」：填一家店提交一条，**无门店维度**——不会按门店聚合展示哪家交了哪家没交。
2. 新版把旧版的门店清单形态（RebateLetterDemo/ShelfCollectionDemo/ContractCollectionDemo）简化丢了——低代码单页形态过于局限。
3. ContractCollectionDemo 手写 1045 行、门店数据写死 49 家，不可复用、不可配置。

## 二、核心抽象

**一个收集任务 = 表单 schema（照片位/字段） + 目标清单（门店们） + 按目标聚合的存储。**

- **目标（Target）**：要收集的对象（门店），有 id（appleId）+ 展示字段（名称/执照/地址/电话/分类）。
- **照片位（Slot）**：由 FormSchema 的 `image-upload`/`upload`/`camera` 字段自动推导（返利函 1 位、陈列 front/back 2 位、柜机协议 1 位）。字段的 `key` 即 slotKey。
- **按目标聚合**：存储键 = targetId；视图 = 目标清单表格。

## 三、与现有体系的关系

| 形态 | 承载 | 数据维度 |
|---|---|---|
| 单页模式（现有） | FormBuilder + FormCollect | 一条条平铺记录 |
| **目标收集模式（新增）** | **FormTargetCollect**（form-builder 家族新成员） | **按目标聚合** |

FormCollect（记录列表）与 FormTargetCollect（目标清单）语义不同，不揉进一个组件。

## 四、组件设计：FormTargetCollect.vue

```
props:
  schema: FormSchema          // 复用现有 schema（照片位字段 + 可选填字段）
  targets: Target[]           // 目标清单（id + 展示字段），来源由宿主给（静态/API/Excel）
  storageKey?: string         // 存储键（同 FormBuilder）
  storageConfig?: StorageConfig // 本地/云端（复用 contract-storage）
  readonly?: boolean

内部：
  1. 从 schema 提取照片位字段（category=upload/image-upload/camera）→ slotKey 列表
  2. 渲染目标表格：每行 = 目标信息 + 每个照片位一个上传组件 + 状态 ✓/✗（全部照片位齐 = 完成）
  3. 搜索（appleId/名称/执照）+ 已收计数
  4. 导出 ZIP：{targetId}-{slotKey}.{ext} 分目录 + 门店数据.xlsx（沿用 ContractCollectionDemo 模式）
  5. 存储：contract-storage 泛化（见下）
```

## 五、存储泛化：contract-storage 扩展多照片位

```ts
interface StoreUploadState {
  contract?: StoreFile        // 兼容旧数据（= slots['contract'] 别名）
  slots?: Record<string, StoreFile> // 多照片位：slotKey → 文件
  ts: number
}
```

- 后端对象名：`{targetId}-{slotKey}-{文件名}`（旧格式 `{targetId}-{文件名}` 兼容解析为默认位）。
- 墓碑/对账/组合后端逻辑不变（已按 targetId 建模）。
- 现有 ContractCollectionDemo 与单测零改动（读 `contract` 兼容路径）。

## 六、三个业务实例化（一套组件）

| 业务 | schema | 照片位 slots |
