# 术语表

本库文档与代码注释里反复出现的词。**先对齐词义，再谈行为** —— 很多误解来自同名不同义。

---

## 架构与产物

### 域（domain）

代码与产物的一级分组，**13 个域入口**：`basic` / `data` / `form` / `feedback` / `nav` / `layout` /
`chart` / `login` / `storage` / `amap` / `route-planner` / `form-builder` / `wc`。

另有 `_internal` 与 `shared` 两个**内部支撑目录**，不出独立域入口（覆盖地板算 14 项 = 12 个域 + 这两个）。

**为什么按域切**：域是**依赖边界**也是**产物边界**。`vcl-ui/basic` 只加载 basic 与共享 core chunk，
不带其他域代码。跨域依赖必须走 `_shared.ts` 这类显式出口，禁止直接引别的域内部路径。

### 入口（entry）

构建产物的一级出口：主入口 + **13 个域入口** + `./css` / `./i18n` 等辅助子路径。
「入口」与「域」基本一一对应，但入口还包括 `wc`（跨框架）这种非业务域产物。

### 接缝（seam）

**宿主与库的契约点**。典型：`FormStore`（表单存哪）、`submitConfig.saveUrl`（提交到哪）、
`setAmapKeys()`（key 注入）、`setActiveFormStore()`（切换存储实现）。

**设计原则**：库不替宿主决定「他的后端长什么样」，只提供接缝 + 一份可实现的契约。

### 自带库（BYO / 自备依赖）

`echarts` / `@vuemap/vue-amap` 这类**大件依赖不在库内打包**，由宿主自己安装。
好处是不绑架版本、不撑体积；代价是宿主必须装对（见 peer 依赖表）。

## 质量与闸口

### 闸口（gate / check）

一条**机械断言**，不通过就非零退出。例：`check:constants`（常量必须有来源）、
`check:docs`（生成的 API 文档与源码无漂移）、`check:i18n`（中英双侧键对账）。

**为什么需要闸口**：靠人工守的纪律一定会回潮。这个库单维护者 + AI，把纪律变成断言是唯一可持续路径。

### 棘轮（ratchet）

一旦变好就**不许变回去**的闸口。

- **覆盖地板**：每域语句/分支/函数覆盖率不得低于实测值下留 2–4 点的地板
- **行数止涨线**：单文件行数上限，只降不升（抬线必须带新的实测理由）
- **噪音棘轮**：单测里未静默的 `console.warn/error` 分类**类别集合**不许出现新类别

「棘轮」这个名字的意思是：只能往一个方向转。所以它天然会带来**假阳性**问题 ——
每个棘轮都必须配噪声抑制（见下）。

### 噪声抑制

棘轮对抗环境抖动的机制。已知三种：

| 场景 | 抑制手法 |
| --- | --- |
| 性能基准（机器负载导致耗时漂移） | 只守护基线 ≥2ms 的场景；用 median 而非 mean；疑似回归**自动重测一次**，两轮都超才判红 |
| console 噪音计数（随机 id 导致类别爆炸） | 归一化随机串/随机 key；**只比类别集合，不比计数** |
| 覆盖地板（个别分支受环境影响） | 地板取实测值下留 2–4 点，而不是顶着实测值 |

### 负向对照

**证明闸口真会红**的动作：故意制造一个违规，确认它非零退出，再恢复。
每新增一道闸口都必须做一次 —— 否则「它一直绿」可能只是因为它从来不检查。

### 留痕（trace）

每次跑闸口都落盘的东西：`reports/quality-check-latest.json`（每步退出码/耗时/失败点）
+ `reports/quality-check-logs/<NN>-<name>.log`（每步完整输出）。

**关键性质**：每次运行前**清空**。混着历史文件就失去「反映最近一次运行」的意义 ——
甚至会让读的人得出反向结论（这件事真发生过）。

### 快链 / 整链

- **整链**（`npm run quality-check`）：27 步，约 10 分钟，**唯一权威**
- **快链**（`--quick`）：6 步，约 1.5 分钟，pre-commit 用

### 覆盖地板（coverage floor）

按域设定的最低覆盖率，低于即红。**全局地板会掩盖域级洼地** ——
全局 54% 全绿的同时，某域可能只有 35%。所以按域设。

## 低代码

### `displaySource` vs `dataSource` —— 最容易混的两个词

| 名字 | 是什么 | 用在哪 |
| --- | --- | --- |
| `displaySource` | **展示元素的数据从哪来** | 表格/图表/地图/结果态等展示类元素 |
| `dataSource`（`FieldDataSource`） | **下拉选项从哪来** | Select / ToggleList 等**输入**类元素 |

`displaySource` 三种模式：

- `kind: 'static'` —— 面板里直接写数据
- `kind: 'field'` —— 绑定到表单字段
- `kind: 'api'` —— 远程拉取（受 `ApiUrlPolicy` 约束）

### `isLayout` / 布局字段

标记为纯展示的元素，**不进提交数据**（`collectVisibleData` 会跳过）。
「这个元素只是给人看，不是给后端收的」——用 `isLayout: true` 表达。

### 字段注册表（fieldRegistry）

**低代码字段类型的单一真源**。新增一种字段 = 往注册表加一条，设计器面板、
渲染器映射、默认值、元信息都从这里取。

### `FormStore` / `RecordStore`

宿主实现的数据接缝：

- `FormStore` —— 表单**定义**存哪（9 个方法）
- `RecordStore` —— 表单**记录**存哪

库内提供 `createRestFormStore({ baseUrl })` 作为参考实现，后端按契约实现几条 REST 路由即可。

### 分享码（share code）

把表单序列化 + **签名**后的字符串，可离线传阅。签名校验不通过会**拒绝渲染**（不是空白）。
码里是 base64，复制不全就解不出来。

## 一致性表达

### 【事实】/【推断】/【建议】

审查与文档里区分这三类。**不确定就标推断，别写成事实** —— 这条纪律比任何单条结论都重要。

### 硬边界（如实声明）

对外文案必须**同硬度**：说了能力，就要在同一处说清限制。
例：「i18n 内置」必须同时说「只有 zh-CN / en-US」；
「无障碍有 axe 值守」必须同时说「无第三方审计、24px 热区尚有登记例外」。

### 口径单一真源

可核验的事实（域数、组件数、用例数、行数）**只在一处生成，其他地方引用不手写**。
手写快照必然过期 —— 实测过 4 个域的行数注释里 3 个已经和现实不符。
