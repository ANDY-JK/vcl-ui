# RTL（从右到左）

::: warning 当前状态：**部分支持**
表单/导航/反馈/数据展示域的**水平间距与边框**已完成逻辑属性转换，
并用双向取证守卫住了；**定位类属性（`left`/`right`）与 `text-align` 尚未改造**。
完整状态见下方「支持矩阵」。
:::

## 契约（宿主需要知道的）

**库内组件不自行设置 `dir`，跟随文档流向。**

```html
<!-- 宿主在根元素设一次，全库跟随 -->
<html dir="rtl">
```

组件内部**不会**写 `dir="ltr"` 去"纠正"自己 —— 那会让 RTL 页面里出现方向错乱的小岛。
唯一的例外是代码/数字等**必须 LTR 的语义内容**（如金额、日期），它们用 `dir="ltr"` 局部声明。

## 已完成（有守卫）

### 1. 逻辑属性转换：77 处 / 32 文件

| 物理属性 | 转为 | 处数 |
| --- | --- | --- |
| `margin-left` / `margin-right` | `margin-inline-start` / `-end` | 46 |
| `padding-left` / `padding-right` | `padding-inline-start` / `-end` | 12 |
| `border-left` / `border-right`（含 `-color`/`-width`/`-style`） | `border-inline-start` / `-end` | 19 |

转换后 `src/components` 内这六类物理属性的命中数**全部为 0**。

### 2. 双向取证守卫 `check:rtl`

7 个代表路由 × `ltr`/`rtl` 各量一遍，断言三条：

1. **零横向溢出**（`scrollWidth <= clientWidth`）
2. **零元素越界**（可见元素 rect 不超出视口左右边界，**排除横向滚动容器内的内容**）
3. **方向确实生效**（`direction === 'rtl'`）—— 防止"测了但没切过去"导致假绿

```bash
npm run check:rtl          # 守卫模式
npm run check:rtl -- --report   # 施工看板（只报告不判失败）
```

已进整链（第 29 步），自起自停 dev server。

### 3. LTR 零回归验证

逻辑属性替换在 LTR 下**应该完全等价**（`start` = `left`），但"应该"不等于"确认"。
用 40 张截图（5 页 × 8 视口）做像素级对照：

- 改前 vs 改后：**40/40 像素完全相同**
- 对照：同代码连截两次也有 10 张不同（图表 canvas 抗锯齿），说明截图本身有噪声基线
- 中途曾出现 1 张 1.56% 差异（`w2560-data-table`），逐文件二分定位后确认是**一次性截图抖动**，
  重截后 0 像素差

### 定位类属性的裁决结果（142 处）

| 档 | 处数 | 判定 | 处理 |
| --- | --- | --- | --- |
| A 可自动转 | **0** | 无 | —— |
| B 保持物理 | 21 | 类名即方位语义（`grid-corner--top-left` 等） | 保持 `left`/`right` |
| D 保持物理 | 7 | 同规则内有 `translateX`（物理量，RTL 不翻转），转了会**错位一倍** | 保持 `left`/`right` |
| C 需人工 | 114 | 贴边/间距锚定，要看它装饰的是起始侧还是固定侧 | 待逐处处理 |

::: tip 一个反直觉的结论
`left: 50%; transform: translateX(-50%)` 看着像"居中"，直觉上该转 `inset-inline-start: 50%`。

**但这是错的**：`translateX(-50%)` 的方向在 RTL 下**不会翻转**，转了之后
`inset-inline-start: 50%` 在 RTL 下变成从右侧算 50%，再向左偏移 50% —— **错位一倍**。

这类"物理居中"本来就与流向无关，应保持物理值。
:::

### 已修的定位类缺陷（本轮）

`.col-fixed-left` / `.col-fixed-right`（表格固定列）从 `left: 0` / `right: 0` 改为
`inset-inline-start: 0` / `inset-inline-end: 0`。

**语义依据**：「固定列」是「钉在**阅读起始侧**」，不是「钉在物理左侧」——
RTL 下用户希望第一列（姓名）钉在右边，因为那才是他开始读的地方。

## 两个守卫的分工

| 守卫 | 管什么 | 判据 |
| --- | --- | --- |
| `check:rtl` | **布局崩坏** | 零横向溢出、零元素越界、方向生效 |
| `check:rtl-semantics` | **方向语义** | 该镜像的镜像了、该固定的没动、**逻辑属性真的生效** |

::: warning 为什么需要第二个守卫
实测发现：在 **142 处 `left/right` 全未转换**的情况下，`check:rtl` 依然全绿 ——
因为「元素跑到错误的一侧」**不会越界**，只是位置不对。

这是守卫的能力边界，必须承认并补上。
:::

### 第三个判据：逻辑属性是否真的生效

判断「逻辑属性生效」不能只看位置，因为 **RTL 下整页翻转**会让位置"看起来对了"。

唯一可靠的判据是**计算样式**：

```
LTR: css.left = 0px     css.inset-inline-start = 0px
RTL: css.left = auto    css.inset-inline-start = 0px   ← 浏览器映射到 right 的证据
```

用 `left: 0` 的写法在 RTL 下 `css.left` 仍是 `0px`。

**这个判据是负向对照逼出来的**：一开始用位置偏移判 mirror/fixed，把
`inset-inline-start` 改回 `left: 0` 后 Δ 依然是 0.972，**探针没红** ——
因为表格整体翻转，`left: 0` 的 sticky 恰好也落到右侧。位置对了是巧合，不是逻辑属性生效。

## 后续怎么继续

1. 先跑 `npm run check:rtl -- --report` 看当前基线（应为 0）
2. 按 `docs/rtl-立项清单-2026-09-30.md` §3 的分期推进 P2（数据展示域定位类）
3. 每改一批就重跑守卫 + 做一次 LTR 像素对照（**这是防"改坏了但测试全绿"的唯一手段**）
4. 全部完成后撤掉 README 的「RTL 硬边界」声明，并按组件更新上面的支持矩阵

::: tip 为什么先建守卫再改样式
立项清单原文：「逻辑属性替换若无 RTL 渲染取证兜底，等于把『LTR 下碰巧正常』换成『双向都可能坏』」。

RTL 改造最危险的形态是：把 `margin-left` 换成 `margin-inline-start`，LTR 下**看起来没变**
（因为 start = left），于是所有既有测试继续绿 —— 而 RTL 下可能整个错位。
**没有 RTL 断言，改动是无风险的假象。**
:::
